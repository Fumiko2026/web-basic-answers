## Q1. インターネットとは

**問題:** 「インターネット」と「Webブラウザで見るホームページ」は同じものですか？違うとすれば、どう違いますか？

**回答:**

同じではありません。
インターネットは、世界中のコンピュータやネットワークを共通のルールで繋いだ例えれば道路網のような巨大なネットワークのことです。
共通のルールとは、通信の決まりであるプロトコルのことです。代表はTCP/IPで、データの送り先や宛先の決め方を定めています。
ホームページは、その道路を使って運ばれる例えれば荷物のうちの一つです。他の荷物（メールなど）も、同じ道路を通ります。サーバーとブラウザで動きます。
日常生活では、ホームページはブラウザで見ます。メールやオンラインゲームもインターネットを使っていますが、WEBではありません。

## Q2. IPアドレスとポート番号

**問題:** このプロジェクトではフロントエンドを `localhost:5173`、バックエンドを `localhost:8080` で起動しています。

- `localhost`とは何を指しますか？
- `:5173` や `:8080` のようなポート番号はなぜ必要ですか？

**回答:**

localhostとは、自分自身のコンピューターを指す特別なホスト名です。IPアドレスで言うと127.0.0.1(ループバックアドレス)に対応します。ネットワークの外には出ず、同じPC内で通信が完結します。
開発中は、自分のPCで動かしているサーバーにアクセスするために使います。

ポート番号が必要な理由

IPアドレスは「どのコンピューターか」を指しますが、１台のPCでは複数のプログラムが同時に通信しています。ポート番号は「そのPCのどのプログラムか」を区別する番号です。住所（IP)が建物、ポート番号は部屋番号というイメージです。

このプロジェクトでは、同じlocalhost上で
・5173（フロントエンド）
・8080（バックエンド）

と別々に動くため、ポート番号で振り分けています。同じポートを２つのプログラムが同時に使うことはできません。

## Q3. DNS

**問題:** ブラウザのアドレスバーに `https://www.example.com` と入力してからページが表示されるまでに、DNSはどのような役割を果たしますか？

**回答:**

DNS（Domain Name　System)の役割は「ドメイン名」をIPアドレスに変換することです。
コンピュータ同士はIPアドレス（93.184.216.34など）で通信しますが、人間が覚えやすいのはwww.example.comのような名前です。DNSはその対応表（電話帳）の役割を果たします。DNSによる名前解決が終わって初めて、サーバーへの接続が始まります。

流れはこうです。
１　https://www.example.comと入力する

２　ブラウザが「www.example.comのIPアドレスは？」とDNSサーバーに問い合わせる。

３　DNSサーバーが93.184.216.34のようなIPアドレスを返す。

４　ブラウザがそのIPアドレスのサーバーに接続し、ページのデータを受け取る。

５ページが表示される。

## Q4. HTTPとは

**問題:** HTTPとは何の略で、どのような役割を持つものですか？「プロトコル」という言葉の意味も含めて説明してください。

**回答:**

HTTP：HyperText Transfer Protocolの略です。

プロトコルとは、通信のルールのことです。人間同士でも言語や話し方が合わないと会話できません。コンピュータ同士も「どんな形式で、どんな順番でやり取りするか」を決めておく必要があり、その取り決めがプロトコルです。

HTTPの役割

WEBブラウザとWEBサーバーの間で、HTML・画像などのデータをやり取りするためのルールです。

・リクエスト：ブラウザがサーバーに「このページをください」とリクエストを要求する。

・レスポンス：サーバーが結果を返す（コード200 OK。404 Not Foundなど）＋データ本体

このプロジェクトでも、フロントエンドがバックエンドのLocalHost：8080にHTTPリクエストを送ってデータを取得しています。

## Q5. HTTPとHTTPSの違い

**問題:** HTTPとHTTPSの違いは何ですか？なぜ現在のWebサイトはほぼすべてHTTPSを使用していますか？

**回答:**

違いは、HTTPSは、HTTPの通信を暗号化したものです。

 HTTPSの「S」は、Secure（安全）の意味で、HTTPにTLS（SSL)という暗号化の仕組みを組み合わせています。

 HTTPSが必要な３つの保護
 １　盗聴の防止：パスワードやクレジットカードの番号を盗み見られない

 ２　改ざんの防止：通信途中でデータが書き換えられない

 ３　なりすましの防止：証明書により本物のサーバーと通信していると確認できる。

そのため、
・公共Wifiなどで盗聴リスクがあるため

・ブラウザがHTTPサイトに「保護されていない通信」と警告を出すようになったため

・無料の証明書が普及し、導入しやすくなったため

・検索エンジンもHTTPSを評価し、HTTP/2などの新しい機能もHTTPS前提のものが多いため

## Q7. HTTPメソッド

**問題:** このアプリのAPIでは以下を使っています。

- GET
- POST
- PUT
- DELETE
- PATCH

これらの「HTTPメソッド」とは何ですか？
日常生活の例えで、それぞれの違いを説明してください。

**回答:**

HTTPメソッドは、リクエストで何をしたいかをサーバーに伝える動詞です。

GET：データを取得する
POST：新しいデータを作成する
PUT:データを丸ごと置き換える
PATCH：データの一部だけ変更する
DELETE：データを削除する

PUTとPATCHの違い：PUTは全項目を送って全部上書き、PATCHは変えたい項目だけ送ります。

400：Bad Request　リクエストの内容が不正　クライアント側の問題
404：Not Found　指定したデータやURLが存在しない
500：Internal ServerError　サーバー内部でエラーが発生した。サーバー側の問題

２XX=成功　４XX＝クライアント（送る側）のミス　５XX＝サーバー（受ける側）のミス


## Q9. JSONとは

**問題:** フロントエンドとバックエンド間でデータをやり取りする際に「JSON」という形式が使われています。

- JSONとは何ですか？
- なぜ広く使われていますか？

**回答:**

JSON(JavaScript Object Notation)は、データを人間にも機械にも読みやすいテキスト形式で表す書き方です。「キー：値」のペアで構成されます。

```json
{
  "id": 1,
  "name": "田中太郎",
  "age": 25,
  "hobbies": ["読書", "映画"]
}
```

なぜ広く使われているか？
・読みやすい：人間が見て理解しやすい
・言語に依存しない：JavaScript ,Python ,Javaなどほぼ全ての言語で扱える
・JavaScriptと相性が良い：ブラウザ上でそのまま変換して使える
・構造化できる：配列や入れ子のデータも表現できる

フロントエンドとバックエンドが別の言語で作られていても、JSONという共通語でやり取りできるのが大きな利点です。


## Q10. APIとは

**問題:** このアプリではフロントエンドがバックエンドのAPIを呼び出してデータを取得しています。

**回答:**

- APIとは何ですか？
Application Programming Interfaceの略
ソフトウェア同士がやり取りするための「窓口」「取り決め」です。

レストランの例えでは、お客さん（フロントエンド）はメニュー（API)を見て注文します。厨房（バックエンド）の中には入りません。メニューに載っている注文の仕方だけが許可されています。

・変更への強さ：DBの構造を変えても、APIの形が同じならフロントエンドを修正しなくて良い。

・再利用性：Web,スマホアプリなど複数のフロントエンドが同じAPIを使える。







## Q11. CORSとは

**問題:** フロントエンド（5173）からバックエンド（8080）にアクセスする際、「CORS」という仕組みが関係します。

CORSとは何のためにありますか？

**回答:**

CORS（Cross -Origin　Rescure Sharing)は、ブラウザが「別のオリジンのサーバー」へのアクセスを安全に制御する仕組みです。

オリジンとは、「プロトコル＋ドメイン＋ポート番号」の組み合わせです。
・フロントエンド：http://localhost:5173
・バックエンド　：http://localhost:8080

ポートが違うので、ブラウザはこれを「別オリジン」とみなします。

CORSが何のためにあるのか？というと

ブラウザには「同一オリジンポリシー」という安全機能があり、デフォルトでは別オリジンへのリクエスト結果をJavaScriptに読ませません。これは悪意あるサイトがログイン中のユーザーになりすまして、別サイトのデータを勝手に読むのを防ぐためです。

しかし、正常な連携まで止まると困るので、CORSがサーバが「このオリジンからのアクセスは許可する」と明治できるようにしています。

動き方はこうです
１　ブラウザがバックエンドにリクエストを送る　Origin ;http://localhost:5173

２　バックエンドが　 Access~contlol-Allow -Origin：http://localhost:5173　を返す

３　ブラウザが許可されたと判断し、JavaScriptにレスポンスを返す

許可がなければ、コンソールに「CORS policyによりブロックされました」とエラーが出ます。

## Q12. クライアントとサーバー

**問題:** 「クライアント」と「サーバー」とは何ですか？

このアプリの構成の中で、それぞれどれがクライアントでどれがサーバーですか？

- ブラウザ
- バックエンド
- データベース

**回答:**

クライアント：サービスを要求する側

サーバー：要求を受けて処理し、結果を返す側

この２つは、通信における役割を表しています。

ブラウザは、クライアントでバックエンドにAPIリクエストを送ります。

バックエンドは、立場が２つありブラウザから見るとサーバー、データベースから見るとクライアントです。ブラウザの要求を受けて処理し、応答を返します。

データベースは、サーバーでバックエンドからのSQLを受けて、データを返します。

## Q14. 3層構造

**問題:** このアプリは

- フロントエンド
- バックエンド
- データベース

の3層構造です。

なぜこのように役割を分けるのですか？

1つのプログラムですべてをやらない理由を説明してください。

**回答:**

理由は５つあります。

１　責任が明確になる　画面はフロント、処理はバック、保存はDB。どこを直せば良いかわかりやすい

２　変更の影響を小さくできる　デザインを変えてもバックエンドは無関係、DBを変えても画面は無関係など余計な手間をかけずに開発できる。

３　担当を分担できる　フロントとバックで並行して開発できる

４　再利用できる　同じバックエンドを、WEBアプリ・スマホアプリ両方から使える

５　セキュリティ　DBに直接アクセスできるのはDBだけ。パスワードや重要なルールをブラウザ側に置かずに済む。DBをブラウザから直接触らせるのは非常に危険である

１つのプログラムにまとめてしまうと

・コードが巨大で複雑になり、修正が難しい

・一部の変更が全体に影響してバグが出やすい

・チーム開発がしにくい

・セキュリティ面でも危険

といったデメリットがあるためです。

## Q16. エンドポイントとURL設計

**問題:** このアプリには以下のAPIがあります。

- `/api/tasks`
- `/api/tasks/{id}`

このようなURL設計の考え方を説明してください。

`{id}` の部分は何ですか？

**回答:**

APIはアプリがサーバーにデータを頼む際の「窓口」です。
エンドポイントは、その窓口の住所で、/api/tasks や　/api/tasks/{id}がその住所に当たります。
URl設計は、住所をどんなルールで決めるかを考えることです。

/api/tasks は、タスク全体のことを指し、/api/tasks/{id}はタスク１つだけを指します。

{id}には、タスク１つ１つに付いた番号（id)が入ります。番号が5なら/api/tasks/5 となります。

URL設計の考え方ですが、
URLには「何を扱うか」（名詞）だけを書き、「何をするか」はHTTPメソッドに任せる考え方をします。
例えば次のようになります。
住所　　　　　　　　メソッド　　　　　　　意味
/api/tasks      GET              タスクの一覧を見る
/api/tasks      POST             新しいタスクを作る
/api/tasks/5    GET              5番のタスクを１つ見る
/api/tasks/5    PUT/PATCH        5番のタスクを直す
/api/tasks/5    DELETE           5番のタスクを消す

住所が整理されて、何をするのかがわかりやすくなるメリットがあります。




## Q17. 同期処理と非同期処理

**問題:** 「同期処理」と「非同期処理」の違いを、日常生活の例えで説明してください。

なぜWeb通信では非同期処理が必要ですか？

**回答:**

同期処理：注文して、その場で立って待つ。出来上がるまで何もできない
非同期処理：番号札を受け取り、席でスマホをみながら待つ、できたら呼ばれる。

WEB通信で非同期が必要な理由
通信には時間がかかります。（数秒）同期だと、その間画面が固まって操作できなくなります。非同期なら、「リクエストを送ったら、返事を待つ間も画面は動き、返事が来たら続きの処理をする」ことができます。

## Q19. 入力チェック（バリデーション）の多重防御

**問題:** 入力チェックはフロントエンドとバックエンドの両方で行うべきと言われています。

なぜ片方だけでは不十分なのですか？

**回答:**

フロントエンドでは、すぐに間違いを教える。空港で例えるとチュックインカウンターの役割です。
バックエンドは、安全性とデータの正さを確認する、保安検査場の役目を果たします。

フロントエンドの入力チェックは、利用者の手元のブラウザで動かしているためプログラムを書き換えられてしまいます。そのため、画面チェックは守りにはなりません。

バックエンドだけでも、安全面は守れます。しかし、使いやすさが悪くなります。入力の間違いがわかるまで、サーバーに送って返事を待たなければなりません。利用者は、間違いにすぐ気付けずイライラします。

つまり、両方で行うと、安全性と使いやすさの両方が得られるのです。

## Q20. エラーハンドリング

**問題:** API呼び出しが失敗した場合（ネットワーク障害やサーバーエラーなど）、アプリはどのように対処すべきですか？

**回答:**

エラーは必ず起きる前提で作ります。

対処の基本は
１　失敗を検知する　try/catch やステータスコード（400、404、500）で判定する

２　ユーザーにわかりやすく伝える「通信に失敗しました。もう一度お試しください。」

３　画面を壊さない　入力内容は消さない　操作できる状態を保つ

４　やり直せるようにする　「再試行」ボタンなど

５　ローディング表示を消す　エラー時もクルクルが回り続けないようにする

６原因調査用にログを残す

エラーの種類と対応は
・ネットワーク障害→「接続を確認してください」
・400（入力ミス）→どこが悪いか表示
・404（見つからない）→「タスクが存在しません」
・500（サーバー異常）→「しばらくしてからお試しください」

## Q23. 主キー（PRIMARY KEY）

**問題:** tasksテーブルの `id` は主キーです。

- 主キーとは何ですか？
- なぜ必要ですか？

**回答:**

主キーとは？：各行を1件だけに特定できる、重複しない番号（ID)です。

なぜ必要か？
同じタイトル「買い物」のタスクが2件あったら、削除する際「どっちか？」わからなくなります。そこで、id=1,id=2のように一意な番号をつけて区別します。

例え：学籍番号やマイナンバー、マンションの部屋番号など同姓同名がいても、間違えません。

主キーの特徴
・重複しない
・空（NULL)にならない
・通常は自動採番

## Q26. インデックス

**問題:** インデックスとは何ですか？

本の索引に例えて説明してください。

**回答:**

インデックスは、検索を速くするための索引を指します。
本の索引に例えると、

・索引なし：ある言葉を探すために、1ページ目から全部めくる

・索引あり：巻末の索引でページ番号を見て、すぐ開ける

## Q27. トランザクション

**問題:** トランザクションとは何ですか？

タスクを別カラムへドラッグ移動する操作で、なぜ重要ですか？

**回答:**

トランザクションとは、複数の処理を「１つのまとまり」として扱い、全部成功するか、全部無かったことにする仕組みです。（オールオアナッシング）

例
「Aさんの口座から1万円引く」→「Bさんの口座に1万円足す」
途中で失敗して「引くだけ」で終わったら、1万円が消えてしまうので、両方成功したら確定（コミット）、失敗したら元に戻す（ロールバック）とします。

ドラッグ移動で重要な理由

タスクをカラム間で動かす時、内部では複数の更新が起きることがあります。

１　タスクのステータスをtodo→doingに変更

２　移動元・移動先の表示順を並べ直す

もし１だけ成功して２が失敗すると、順番がゴチャゴチャになったり、データに矛盾が生まれます。
トランザクションなら、失敗時に全部元通りになるので混乱が起きません。

## Q28. SQLとORM

**問題:**

- SQLとはどのようなものですか？
- ORMの役割とは何ですか？

**回答:**

SQL（Structured Query　Language）とは、DBに命令するための専用用語です。構造化問い合わせ言語と訳されます。DBへの注文書のようなものです。

ORM（ObjectーRelational Mapping)とは、プログラムのオブジェクトとDBのテーブルを、自動で対応づけてくれる仕組みです。
役割は、
・SQLを自動生成してくれる
・DBの行とJavaオブジェクトの変換を自動化してくれる
・コードが短く読みやすくなる

ORMは「通訳」で、Javaの言葉（オブジェクト）とDBの言葉（テーブル）を翻訳してくれます。

## Q29. バージョン管理（Git）

**問題:** Gitなどのバージョン管理システムとは何ですか？

なぜ必要ですか？

使わないとどんな問題が起きますか？

**回答:**

Gitとは、ファイルの変更履歴を記録・管理するシステムです。「いつ・誰が・何を・なぜ変えたか」が残ります。

なぜ必要か？
・間違えても過去の状態に戻せる。

・誰が何を変えたかがわかる。

・複数人で同時に開発しても。変更を統合できる。

・新機能のチェックを安全に行える。

使わないと起きる問題
・app_最終.js,app_最終_本当の最終.js,app_最終２.js・・・とファイルが増える

・同じファイルを2人が編集し、片方の変更が上書きされて消える

・バグが起きても、どこで壊れたのかわからず、戻せない

・誰が変えたかわからず、責任や原因を追えない



## Q30. ブランチとPull Request

**問題:**

- ブランチとは何ですか？
- Pull Request の目的は何ですか？
- なぜ全員が main に直接変更しないのですか？

**回答:**

○ブランチとは、本流（main)から枝分かれした、作業用の独立したいわば下書き用のコピーです。

例：feature/loginブランチでログイン機能を作る。mainには影響しません。

○PULL Requestは、「この変更をmainに取り込んでください」という依頼です。

・取り込む前に、他のメンバーがコードをレビューし、
・自動テストを実行したり、
・変更内容の議論や記録が残るようにしたい

といった目的があります。

○なぜ、mainに直接変更しないのか
・mainは「常に動く、完成品の状態」を保つべき場所なので、未完成のコードやバグを直接入れると、全員の作業が止まってしまうからです。

・また、誰かの変更で他の人の作業が壊れるのを防ぐためです。

例えれば、mainは本番の原稿で、ブランチは下書きのコピー、下書きで書いて先生（レビュワー）にチェックしてもらってから、本番原稿に反映するイメージです。


## Q31. コミットメッセージの重要性

**問題:** 例：

`feat: ログイン機能を追加`

良いコミットメッセージを書くことがなぜ重要ですか？

**回答:**

コミットメッセージとは、変更内容を説明する一言メモです。

良いメッセージが必要な理由

１　履歴を読んで、何をしたか一目でわかる。

２　バグ調査が早くなる（いつ壊れたかを探しやすい）

３　レビューする人が理解しやすい

４　将来の自分や新メンバーが助かる

５　戻す、取り消す時の判断材料になる

良い例：fix:タスク削除時にエラーになる問題を修正

featなど接頭辞（プレフィックス）の意味
feat:新機能
fix:バグ修正
docs:ドキュメント
refactor:動作を変えない整理

接頭辞があると、種類が一目で見て分かりやすいです。


## Q32. なぜ技術的な仕組みを理解すべきか

**問題:** AI時代においてコードはAIが書けるようになりました。

それでも

- ネットワーク
- データベース
- Webアプリケーションの仕組み

を理解する必要がある理由を、あなたの考えで述べてください。

**回答:**
AIがコードを書ける時代になっても、技術的な仕組みを理解する必要がある理由を４つ挙げたい。

１　AIの出力が正しいか判断するのは開発者である。
AIがコードを書けるようになったが、常に正しいとは限らず、勝手に開発者の意図を判断し、暴走してしまうこともある。AIは間違ったコードも自信を持って出してくるので、仕組みを知らないと間違いに気づけないことも考えられる。

２　問題が起きた時、原因を特定し、的確な指示が出せるのは開発者である。
「CORSエラー」「保存されない」といった問題が起きた時、仕組みを知っていれば、どの層の問題か切り分けて対応できる。また、「タスクを保存して」と指示するより、「POST/api/tasksでDBに保存して、バリデーションはバックエンドで行って」と指示した方が、良いコードが出てくる。

３　セキュリティや品質の責任は開発者にある
AIが書いたコードで情報漏洩が起きたり、質の劣った開発を行ったりしたら、責任を負うのは開発者である。

４　設計は開発者の仕事である。
要件定義書をはじめ、「何を作るか」「どう分けるか」は、仕組みの理解がないと決められず、それは開発者の能力にかかっている。

AIによって驚くほど短時間に、多くのことができるようになったがそれを使いこなす土台は開発者である自分の理解にあると考えている。
